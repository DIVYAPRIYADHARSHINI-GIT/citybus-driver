03 Production commands

Run from the backend root directory. Apply migrations and seed data before starting the service:

python -m alembic upgrade head
python -m app.seed

Exact single-worker start command:

python -m uvicorn app.main:app \
  --host 0.0.0.0 --port "${PORT:-10000}" --workers 1

Use one service instance, no horizontal autoscaling and no production --reload. The host supplies PORT; 10000 is the fallback. Health-check path: /health (200 when ready, 503 when storage/schema/seed is unavailable or unprepared).

Backend securityENVIRONMENT=production, COOKIE_SECURE=true, exact HTTPS CORS_ORIGINS and the appropriate COOKIE_SAMESITE policy.
Cookie compatibility matters. Use SameSite=Lax with same-site HTTPS custom domains. Unrelated Vercel/Render sites require SameSite=None; Secure, but browser third-party-cookie blocking can still prevent refresh. Same-site custom domains or the documented REST proxy are preferred.

05 Known limits and release checks

  • Cold starts: sleeping hosts may exceed client connection timeouts. An always-on backend is recommended for reliable multiplayer.
  • Single-process rooms: restarts/deployments end live rooms and reconnect reservations. Committed accounts, saves, company data and rewards remain in PostgreSQL.
  • Not live-verified: actual Vercel/Render deployment, public TLS/WAN behavior, host Linux installation/capacity and target-device cookie policies.
  • Product scope: hosting preparation does not close the remaining art, simulation, moderation, device or endurance gaps documented in the Stage 6 report.

Next step: create the managed database and persistent backend, configure real domains and secrets, deploy the Vercel frontend, then test health, login/refresh, cloud conflict handling, WSS rooms/reconnect and offline play on the live version.

Supporting documentation: DEPLOY.md contains the full deployment guide, environment-variable tables and live acceptance checklist. frontend/docs/STAGE6.md records the game implementation, measured results and remaining product limits.
Release boundary: locally tested hosting preparation — not a public deployment or production-capacity certification.

06 What was faced and how it was handled

CHALLENGERESPONSE AND CURRENT STATUS
Cross-origin authentication
Separate frontend/backend sites change how refresh cookies behave.		Addressed locally: added configurable SameSite policy with Secure/HttpOnly cookies and exact CORS origins. HTTPS subdomain refresh was verified. Third-party-cookie blocking on unrelated sites remains a live-browser risk.
Production endpoint differences
A local Vite API proxy does not exist automatically on a static Vercel deployment.		Implemented and verified: separate public REST/WebSocket variables, local defaults and HTTPS-to-WSS enforcement. A real secure room handshake passed without a Vite API proxy.
Misleading offline emulation
A real serving-process shutdown exposed blank reloads that page-level emulation had missed.		Fixed and verified: the cause was an Origin/Vary mismatch for cached modules/styles. Static-cache matching was corrected while keeping API responses excluded. Cached reload and touch driving passed with the serving process stopped.
Landscape touch controls
At 844 px wide, a width-only breakpoint hid the pedals on a touch viewport.		Fixed and verified: capability-based layout restored the controls. Tests checked unobstructed 44 px-or-larger targets and actual touch acceleration, braking and release at three landscape sizes.
Multiplayer timing jitter
A legitimate physical movement update was rejected as a jump during a three-player browser race.		Corrected within basic anti-cheat scope: added bounded receipt-jitter allowance while retaining sustained speed/jump checks. Successful reruns had zero rejected legitimate updates; this is not cheat-proof server physics.
Graphics and memory lifetime
Trailer and instanced resources needed explicit disposal; longer-run process memory still grew.		Partly resolved: cleanup and regression checks were added. Short rendering checks were stable, but logical-soak RSS growth and long GPU/Android behavior still require profiling. No leak-free claim is made.
Incomplete deployment/device evidence
Local checks cannot establish live-host behavior or real Android/controller performance.		Still open: no public deployment, Docker execution or actual Android acceptance was performed. The report records those limits and provides a live release checklist instead of treating them as passing tests.

Design evaluation

Advantages & disadvantages.

Evaluation of CityBus Driver’s offline-first game and separate frontend/backend deployment model.

07 Strengths and trade-offs

Advantages

  • Offline resilience. Installed local driving and saves remain usable when the API is unavailable; online features are optional.
  • Clear hosting separation. Static frontend assets can be delivered independently, while a persistent backend maintains long-lived WebSocket connections.
  • Durable, controlled progress. PostgreSQL, versioned saves and explicit conflicts protect server-owned data. Stable operation IDs prevent repeated financial effects in the tested flows.
  • Reusable game systems. Shared vehicle profiles and route graphs support different buses and regions without replacing the driving foundation.
  • Secure configuration boundaries. Signing/database secrets stay backend-only; HTTPS/WSS and HttpOnly refresh cookies are supported.
  • Repeatable verification. Unit tests, database tests and real-input browser checks make regressions easier to detect and reproduce.

Disadvantages / limitations

  • More operational complexity. Two hosts require coordinated URLs, CORS, TLS, cookie settings, migrations and frontend rebuilds.
  • Limited room scalability. In-memory rooms require one process/instance. Restarts lose live rooms; horizontal scale needs additional architecture.
  • Browser-dependent sessions. Third-party-cookie restrictions can break refresh across unrelated sites even when initial login succeeds.
  • Device performance uncertainty. Three.js rendering can be demanding. Desktop results do not guarantee stable frame rates or thermal behavior on mid-range Android devices.
  • Storage and trust boundaries. Local storage is quota- and origin-dependent; active-world cloud resume is absent. Offline result plausibility checks cannot prove honest driving.
  • Unfinished product polish. Simplified physics/NPCs, shared procedural interiors, incomplete localization and operational/moderation gaps remain.
Overall assessment: this model is a useful, tested foundation for an offline-capable bus game with optional cloud and multiplayer services. It is not yet a fully polished commercial simulator or a proven large-scale public service.

Recommended priorities

  1. Verify the live deployment, refresh-cookie behavior, backups and restart handling.
  2. Test real Android/controllers and complete longer rendered, network-loss and route/model/weather acceptance runs.
  3. Improve art/interiors, simulation detail and production operations before making stronger realism or capacity claims.

Advantages describe implemented design properties, not guarantees of zero downtime, unlimited scale, cheat-proof play or absence of memory leaks.
